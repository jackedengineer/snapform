# ADR-018: Separate respondent capabilities

Accepted 29 October 2026. Respondents do not need creator accounts. Use a dedicated random 256-bit bearer credential per response session, sent in Authorization rather than a URL. Store only its SHA-256 hash in Neon. It cannot authenticate account/control API requests. The client transport will keep it scoped to the form/tab, warn when browser recovery storage is unavailable, and never send it to an embedding parent or operational logs. Cookie-dependent cross-site account authentication is not a requirement for embedded intake.

Each response session has immutable tenant/form/version identity and an absolute 24-hour expiry. A later publication does not reinterpret its answers. Unpublishing revokes access and further starts. Session reads require matching public identity, session identity and capability hash in transaction-local settings, plus an active publication and unexpired session. Private account context is cleared before applying this scope. Creator membership alone does not expose an unfinished respondent draft.

The restricted runtime cannot insert session rows directly, delete them, or change their tenant, version, credential, expiry or status. It may update only answer data, revision and update time under the capability policy. Fixed-path SQL commands derive ownership/version from the live publication and take a shared publication lock during creation. They return only the pinned definition and safe session state. PUBLIC execution is revoked. The access predicate must be created after its table and before its RLS policies; migration 0010 explicitly preserves that dependency order.

The answer document has a 2 MiB database bound so fifty maximum-length Unicode text answers can fit; field-level HTTP mutation limits and validation will remain separately bounded. Incomplete answer handling, idempotent mutation receipts, reviewed durable submission, retention and billing/abuse checks are subsequent slices, not inferred from session creation. Real expiry and browser-storage failure journeys remain explicit collector release checks. No ordinary runtime privilege is broadened just to manufacture expiry fixtures.
