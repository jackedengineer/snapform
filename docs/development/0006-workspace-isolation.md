# Workspace data and authorization foundation

28 October 2026. The same Neon database now has workspace and membership tables, explicit runtime grants, role constraints and row policies. Migrations 0002–0004 were reviewed and applied forward; an applied migration was not rewritten. Auth tables and credentials remain separate from business tenant context. No second database or branch was created.

Workspace creation inserts the workspace and its initial owner in one transaction. The browser-generated operation UUID deduplicates retries; an existing workspace is returned only to its owner when the submitted fields agree. A collision cannot create a membership or overwrite another workspace. Duplicate lookup targets the ID directly rather than depending on a bounded list page. UUIDs normalize to lowercase; names match PostgreSQL's character minimum and reject null/malformed Unicode before SQL. The same text guard protects account names. Native string APIs are sufficient. TypeScript now includes ES2024 library declarations (syntax target stays ES2022), matching the selected modern browser/Node 24 baseline; no polyfill is added.

Server-only helpers accept an authenticated actor ID, authorize membership/action first and set user/workspace/role transaction-locally on the same Neon Client. The pure role matrix permits viewer reads, editor operations/export/destinations and owner administration. Unknown roles/actions fail closed. These helpers are not exposed as a public SQL/context-setting interface. Last-owner mutations and invitations are subsequent operations, not claimed implemented here.

Real restricted-login tests cover atomic owner creation, duplicate/collision behavior, cross-tenant reads, denied foreign membership insertion, viewer write denial and context cleanup. A test initially found three visible memberships instead of two: an active workspace context still allowed the user's memberships in other workspaces. Migration 0004 restricts selected-context membership reads to that workspace; unselected identity context can list the user's own memberships. The test now passes. A separate test proves transaction-local context clears while reusing the exact same PostgreSQL backend connection, including after a committed settings-only transaction. All synthetic business/identity rows roll back.

The current ten database tests pass. Workspace/account text tests first failed for malformed input and then passed with the native guard; all implemented pure contracts remain fully covered. The initial list helper is bounded to 100 entries. Public HTTP operations, workspace screens and their three-persona browser gate are the next slice; this internal foundation does not complete workspace V1.

Sources: [PostgreSQL 18 row policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [Drizzle transactions/savepoints](https://orm.drizzle.team/docs/transactions), [native Unicode validation](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/isWellFormed), existing FR-01–03 role contract.
